# RLS audit

Every table in `public` has row level security enabled. The iOS API uses the service role after it checks the caller, so these policies are the backstop for the operator and admin portals (user JWT) and for any direct client query.

Roles below mean a policy exists for that role. "None" is intentional and is not service-role-only.

## Service-role-only

No `public` table is service-role-only.

`job_runs` is the closest case: authenticated users cannot insert, and only an admin can select. The cron job writes through a security-definer function, which is the same path the service role would use. That keeps the schedule's history out of customer and operator clients without hiding it from an admin.

`audit_events` is admin-read and service-role-write. Customers and operators have no policy. The service role bypasses RLS; `authenticated` cannot insert.

`auth` and `storage` objects are outside this list. `storage.objects` for `aircraft-photos` is public-read with operator or admin write, from `0001_init.sql`. `storage.objects` for `trip-documents` is private. Operator members on the trip, the customer, and admins can read. Operator members and admins can write. Paths are `{trip_id}/{file}`. `storage.objects` for `invoices` is private. The customer on the booking and admins can read. Admins can write. Paths are `{invoice_id}.pdf`. The API uploads with the service role. `storage.objects` for `operator-documents` is private. Paths are `{operator_id}/{file}`. Admins can read and write. Operator members can read objects under their own operator id. `0022_operator_verification.sql`.

## Regression suite

`supabase/tests/rls/` is a `node:test` suite with no extra dependencies. The `migrations` job in `.github/workflows/web-ci.yml` runs `node --test 'supabase/tests/rls/**/*.test.mjs'` after `supabase db reset --local`. Locally: `supabase start && supabase db reset --local && node --test 'supabase/tests/rls/**/*.test.mjs'`. The directory argument does not discover these files on Node 25, so CI passes the glob.

The suite signs in with GoTrue password grants for a seeded customer (Alex Rivera), Northline (operator A) and Atelier (operator B), plus a platform admin and a non-admin Northline member created during setup. It checks the 0031–0035 triggers and the cross-tenant reads called out in KOR-70.

Known-allowed: an operator with a `declined` `trip_request_operators` row can still select `trip_documents` for that trip. `operator_can_access_trip` (0005) does not look at fan-out status. The suite records the observed row count and does not fail the build on it.
